The idea

Commercial "company harness" platforms put agents inside a company's chat workspace, give them tools, memory, sandboxed code execution, and scheduled background work. This project builds the same five components — framed by LangChain's "The five components of building a company harness" — as an open, deterministic, offline-first Python package, so the policy questions can be studied and measured: whose identity does an agent act under? What may one user's agent tell another user? How does generated code call a service without ever holding its secret?

The answers are enforced, not documented: an identity broker decides every tool call (on-behalf-of, service, or dual), blocks violations and logs them, and stamps every action with the acting identity. Memory isolation is a wall with exactly three promotion gates. Services are reachable only through a secret proxy that validates scoped, short-lived capability tokens — raw credentials never enter the sandbox.

The five components

1 · Lives where people work

Workspace model of channels, DMs and threads. Conversations break out into agent-owned threads so agent work stays out of the human thread. Chat-adapter seam with an offline stub.

2 · Identity broker

Every tool declares ON_BEHALF_OF, SERVICE or DUAL. Per-surface gating (mail is DM-only), per-operation whitelists, approval gates. Violations are blocked and logged — never silently rerouted.

3 · Two-tier memory

Global tier plus per-user tier with enforced isolation and provenance on every fact. Promotion only by owner consent, multi-user corroboration, or a declared-global route that refuses user-sourced content.

4 · Sandbox + secret proxy

Deterministic sandbox seam plus a real subprocess implementation with a scrubbed environment. The proxy injects credentials host-side; the sandbox sees only scoped, short-lived capability tokens.

5 · Ambient scheduler

Cron-style interval/daily schedules and event triggers. Agents register schedules on a user's behalf. Ambient runs are budgeted and audited exactly like invoked runs.

Managed layer

Declared agents, run traces, per-step token/cost accounting, a budget governor, and human-approval gates — carried over from open-managed-agents.

Quickstart

pip install open-company-harness
PYTHONPATH=src python3 examples/quickstart.py
PYTHONPATH=src python3 demo.py            # scripted Meridian Labs day
PYTHONPATH=src python3 -m pytest tests/ -q # 53 tests
PYTHONPATH=src python3 experiments/run_experiments.py

The bundled scenario is a fictional company, Meridian Labs: four users, five channels, five tools (code host, CRM, mail, docs, social), three agents. A demo workspace UI (React + FastAPI + GraphQL) ships in the repo under demo/ with a ready Render blueprint — deploy-ready, not deployed.

Honest limitations

The subprocess sandbox is a process boundary, not a hardened container — it does not itself block networking or filesystem access. Capability tokens are visible inside the sandbox by design; they are opaque, single-service, single-run and short-lived, and E3 is the evidence they are useless outside their scope. Memory corroboration uses strict lexical token-set equivalence, so paraphrases do not promote. Experiments run on the scripted provider over declared task templates; nothing here measures model behaviour.
